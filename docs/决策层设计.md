# 决策层设计：判断、决策、领导力

## 1. 缺口的精确表述

DSH 的 `agent-loop` 是 **task-execution loop**，不是 **goal-seeking loop**。

- task-execution：用户给一个 turn → 模型决定调什么工具 → 产出 → 结束。成功标准是"这个 turn 完成"。
- goal-seeking：有跨轮次目标 → 持续评估"离目标多远 / 方向对不对 / 要不要换 / 证据够不够" → 成功标准是"目标达成或确定不可达"。

DSH 提供了执行所需的一切结构，但没有提供**取舍**的结构。

`ctx.agentLoop` 在接缝表中的类型是 `bundle`，描述为"唯一的具体循环插件；扩展包依赖 dsh-agent 的事件和服务，而不依赖此包"。→ **替换循环是被允许的**，但下游只认 `dsh-agent` 的事件/服务契约。

已有的三件半（都是「状态」，不是「判断」）：

| 接缝 | 它给什么 | 它不给什么 |
|---|---|---|
| `ctx.goals` | 从会话日志折叠出带修订版本的目标状态 | 该不该追这个目标、何时放弃 |
| `ctx.planMode` | 折叠计划/模式状态；**渲染由部署方拥有的指导信息**；注册 `/plan` | 计划好坏、该不该改 |
| `ctx.agentTeams` | 持久化共享任务板、任务归属、依赖 | 先做哪个、做完怎么算够 |
| `ctx.agentLoop` | 可替换的循环实现 | 循环里没有"元决策"阶段 |

---

## 2. 三个具体缺口

### 2.1 决策不可审计

DSH 里模型做决定是隐式的：在 turn 里想一下，然后调工具。没有留下：候选集、选了哪个、依据哪条证据、放弃了什么、什么观测会证明它错了。

后果：事后无法复盘；无法做"有决策记录 vs 没有"的对照实验；无法满足项目摘要 §9「经复核的有效发现」的复核要求。

### 2.2 转向与放弃没有触发器

goal 有 `blocked` 动作，但条件是"同一阻塞条件持续 3 轮"——**被动**。

主动语义没有：这个假设已被证伪，别再试了；这条路径信息增益为零，换方向；这个 worker 连续失败，换执行单元。

### 2.3 停止条件缺失

没有"证据饱和"概念。loop 只在 turn 结束时停，不在"够了"时停。

## 3. 落点：三层同时下手

领导力不是某一个 Service 能给的。必须三层配合，缺一层就退化。

### 层 1 · 指令层（提示词）

- `ctx.systemPrompt` 是各插件贡献提示词段的收集器 → 贡献"决策框架"段
- `ctx.planMode` 的指导信息**归部署方所有** → 贡献"规划纪律"段
- `ctx.persona` 可换 → 领导者的行为约束

这一层便宜、见效快，但**只有提示词就是空话**，必须配层 2 和层 3。

### 层 2 · 结构层（决策记录）

新 Service + `ctx.sessionProjections` 注册投影，让决策记录随 session log 持久化、可 replay、可导出。

每条决策记录（Decision Record）：

```
decision_id
candidates[]        候选方向/动作/假设
chosen              选了哪个
rationale           依据（必须引用 evidence_refs，不能是自述）
rejected[]          放弃了什么 + 各自理由
falsifier           如果这个决策错了，什么观测会暴露它
saturation          认为证据够了的判据
reversible          是否可逆 / 回滚代价
```

关键约束：`rationale` **必须引用 evidence_refs**。没有证据引用的决策记录视为无效。这一条把"决策"钉在证据体系上，防止它变成叙事。

### 层 3 · 执行层（硬约束）

`ctx.tools.guard()` 的单调拒绝语义，把决策纪律变成不可旁路的拦截：

- 目标不在授权范围 → 拒绝
- 预算超限 → 拒绝
- 对已证伪路径的重复测试且无新证据 → 拒绝
- 声称 `confirmed` 但 evidence_refs 为空 → 拒绝

这一层不是提示词，是代码。任何插件都放行不了别的 guard 已拒绝的调用。

## 4. 反面：领导力会退化成乱决策

给 LLM 自由决策权的典型病理，必须在设计时就要堵：

| 病理 | 堵法 |
|---|---|
| 频繁换方向，永不深入 | 转向必须附新证据；无新证据的转向由 guard 拒绝 |
| 过度规划，不执行 | planMode 产出的计划必须在 N 轮内产生第一个可验证动作 |
| 过早宣布成功 | `confirmed` 必须带可重放的 evidence_refs |
| 无新证据的重复驳回 | 呼应项目摘要 §3 的既有原则，落到 guard |
| 假设不可证伪 | 假设必须带 falsifiable_by，否则不进任务板 |

---

## 5. 一个容易漏掉的前提：领导力包含"可以先不做"

DSH 的 loop 是顺从的：给了任务就做。但领导力包含"这件事该不该现在做"。

DSH 里唯一允许"先不做、先谈"的结构是 **planMode**。对安全测试尤其关键——目标是否在授权范围内，必须先确认再动手。这对应项目摘要里「皇帝」的裁决点和 §7.3 的边界检查。

所以 planMode 不只是"规划功能"，它是**授权确认的唯一入口**，优先级比想象的高。

---

## 6. 与既有方案的关系

这一层就是前面方案里"调度语义"的实际内容。顺序上应排在预算闸之后、网络出口之前：

1. 预算闸（guard，最小可验证）
2. **决策记录（本次设计）**
3. 假设/实验/判定的领域语义
4. 网络出口

## 7. 核实结果（源码实测，未运行时验证）

核实基准：`/root/dsh-test/pkg-0.1.5-rc.1` 编译产物。

### 7.1 blocked 的「3 轮」是软约束，不是硬约束

`dsh-tool-goal/lib/index.js:115`：

```js
const Config = z.object({ blockedAfterConsecutiveRounds: z.number().step(1).min(1).default(3) });
```

这个值只进 `guidance(blockedAfter)` 生成的**自然语言提示词**：

> "Mark blocked only after the same blocking condition persists for at least ${blockedAfter} consecutive goal rounds... difficulty, uncertainty, or useful remaining work is not blocked."

硬校验只有 `resolveCompletionAuthority`：

> "complete and blocked require a direct human turn or the current goal round"

即：代码只校验**你有没有权限调这个动作**（必须是人类直接轮次或当前 goal round），**不校验你等够了没有**。

`dsh-goal` 第 205 行只有 phase 转换校验（`active → blocked`），无轮数逻辑。`dsh-goal-round-driver` 只有 `maxGoalRounds` 上限（第 125 行），也无 blocked 计数。

**结论：DSH 自己把最关键的决策纪律放在提示词里。** 这正说明决策层的硬约束必须自建，不能指望上游。

### 7.2 不需要替换 agentLoop——`agent/pre-step` 就是落点

`dsh-agent/lib/index.js:160` 的既有监听器揭示了机制：监听器签名是 `({ agent, messages, signal, step }, next)`，可以 `await next()` 取下游决定，再返回改写后的决定，还支持 `{ prepend: true }`。

`dsh-agent-loop/lib/index.js:894` 的实际调用：

```js
const decision = await this.dispatch.waterfall("agent/pre-step", {
    messages: claimed,
    ...position,     // { turn, step }
    signal
}, () => Promise.resolve({
    kind: "enter",
    messages: context === void 0 ? claimed : [...claimed, context]
}));
```

消费端（第 903、941-949 行）：

- `decision.kind === "reject"` → `turnEnds = { kind: "blocked" }`，turn 以 blocked 结束
- `decision.messages.length === 0` 且 `turnEnds` 已设置 → 跳出循环
- `phase.step === 0` 且 `messages` 为空 → `turnEnds = { kind: "completed" }`

**所以一个 pre-step 监听器就能拿到完整的三件事：**

| 决策意图 | 实现 |
|---|---|
| 判断（要不要做这一步） | 返回空 messages → turn 结束 |
| 决策（拒绝方向 / 越界 / 已证伪） | 返回 `{ kind: "reject" }` → turn 以 blocked 结束 |
| 领导（注入方向、改策略） | 往 `decision.messages` 追加内容 |
| 证据饱和（该停了） | 返回空 messages → completed |

而且是 async，可以等待外部判定（小模型、规则引擎、你的领域服务）。

**成本从"重写 1936 行循环"降到"注册一个 waterfall 监听器"。**

### 7.3 顺带确认的两个额外落点

- `agent/request` 也是 waterfall（第 1143 行）：模型请求前的最后一道，可改 provider/model/参数 → **预算 enforcement 的第二个落点**
- `agent/request-error` 也是 waterfall（第 1088 行）：错误可拦截 → 失败重试策略、熔断的落点

### 7.4 一个时序约束

`preStep` 里 `systemPrompt.assemble()` 在 waterfall **之前**执行（第 889 行）。所以 pre-step 监听器拿到的不是系统提示本身，而是已组装的 messages。

→ 决策层要影响提示词，只能通过**追加 messages**，不能修改已组装的系统提示段。要改系统提示，得走 `ctx.systemPrompt` 的贡献机制，那是另一条路（层 1）。

### 7.5 反例：pre-step 的顺序不保证，安全闸不能放这里

cordis 的 waterfall 监听器顺序实现（`cordis/lib/index.js:336`）：

```js
const method = options.prepend ? "unshift" : "push";
```

以及第 1796 行：`Entries added closer to the root apply first; base is prepended and ...`

即：`prepend: true` 是 `unshift`，**后注册的反而更靠前**（栈序）。

**推论（推翻本文档 §3 层 3 的一个隐含假设）：**

`agent/pre-step` **不能**承担安全闸职责。如果两个插件都 `prepend`，你的安全闸可能被后注册的监听器抢到前面先跑、甚至被改写决定。

安全闸必须放在 `ctx.tools.guard()`——它是**单调拒绝**语义（"no guard can force-allow a call another guard denied"），与注册顺序无关。这是唯一的正确落点。

**分工修正：**

| 层 | 只做 | 不做 |
|---|---|---|
| `agent/pre-step` | 判断、决策、领导、停止 | 安全拦截 |
| `ctx.tools.guard()` | 安全拦截、预算拒绝 | 决策与叙事 |
| `agent/request` | 模型请求前的最后一道（参数/路由） | 同上 |

### 7.6 planMode 的指导信息是配置字段

`dsh-plan-mode/lib/index.js`：第 9 行 "deployment-owned guidance section is included in each model request"；第 50 行校验 "Missing, blank, non-string" 均失败；第 139 行注释 `Validated deployment-owned guidance`。

→ 注入方式就是 **cordis.yml 里 `plan-mode` 条目的一个必填字符串配置**，每次模型请求都会带上。不需要写服务调用。

### 7.7 已核实：pre-step 的作用域向下继承

`dsh-scope/lib/index.js:234`：「scope nesting: registration views inherit DOWN the chain (a child scope ...)」；第 146 行明确「不得静默拾取祖先的注册 —— 需要继承时用 `chainLayers`」。

`dsh-agent` 的 `agentCarrier(agent) = scopeTarget(agent, agent)`，事件以 carrier 为 scope 分发。

→ 注册在 root agent 的 `agentCtx` 上的 pre-step 监听器，落在其 scope 链上，子 agent 可继承。**领导力理论上可覆盖整棵树。**

**未核实**：agent 创建时是否真的把子 agent 的 scope parent 设为父 agent 的 ctx。scope 机制支持不代表实例化时接上了。

### 7.8 已核实：决策记录用独立投影，复用 agent-team 的模式

`agent-team` 的四项设计承诺（README 原文）：

- **One tree identity** —— 由 subagent runtime 解析 root，Team 不维护第二份成员权威
- **Durable log, derived state** —— Lead log 拥有 tasks 与 child catalog facts；每个目标 Agent 拥有自己接受的消息
- **Explicit authority** —— 每个服务方法都必须传活的调用 `Agent`；owner 或 Lead 改任务，只有 Lead 能重分配
- **Bounds that fail loud** —— `maxTasks` 是验证过的部署值，耗尽报 typed error 而非复用 id

源码角色划分：`task-board.ts`（Task CAS 命令、DAG 校验、派生视图）、`journal.ts`（串行化 Lead-log 事务与提交通知）、`projection.ts`（重放 mode 与 task 记录，发布 `agentTeam` 客户端视图）。

→ **决策记录应采用同一模式：session log + 独立 projection，不并入 task board。** 理由：粒度不同（Task 是「谁做什么」，Decision 是「为什么这么选」）；决策写入要校验 `evidence_refs`，任务板不需要；两者用 id 关联即可。

### 7.9 仍未核实

- 子 agent 的 scope parent 是否真的指向父 agent 的 ctx（决定领导力能否一注册覆盖整棵树）
- `agent/pre-step` 在 goal round（`source.kind === "goal"` 的注入消息）与普通用户轮次上的行为差异
