# 奶虫 · 定位与边界

## 这是什么

一个**真实渗透作业的编排引擎**：带时钟、收敛、可证伪假设循环、跨轮记忆、
授权范围闸、扫描产物查询、攻击路径推理、以及受内核监管的执行层。

覆盖两类作业形态：

- **黑盒**：只有域名 / IP 段 / URL，没有源码与内部信息
- **白盒**：有源码、配置、IaC、架构文档

两者不是同一个 prompt 换个参数，是**两套方法论**
（`agents/blackbox.md` 与 `agents/whitebox.md`）：

| | 黑盒 | 白盒 |
|---|---|---|
| 输入 | 外部可见信息 | 源码 / 配置 / 架构 |
| 第一动作 | 资产发现 → 指纹 → 攻击面枚举 | 入口点清单 → 信任边界 → 数据流追踪 |
| 核心方法 | 从响应差异反推内部结构 | 从代码路径推导可达性 |
| 判定依据 | 对照实验（Body-Diff / 唯一性 / 可重放） | **代码位置 + 实际请求**双证据 |
| 主要误报源 | 把版本号当结论、把单次差异当漏洞 | 把"看起来危险"当"实际可利用" |
| 典型高估 | 影响范围 | 可达性 |

两份规格里都写了"何时该转另一种"——黑盒在证明不了可达时转白盒，
白盒在判断不了真实暴露面时转黑盒。同一份报告里两种视角都该有。

## 不是这是什么

**不是 CTF 工具。** 从 2026-11-20 起不再用于解题。

差异不只是措辞。CTF 是封闭题、有唯一答案、可完全复现、有平台判定对错；
真实渗透是开放环境、没有标准答案、不可复现、只有客户和报告。
这套东西里凡是为前者设计的东西都已被移除或改写：

- 移除了 flag 提交、平台判定、容器生命周期管理、分值跟踪
- 移除了"绕过提交门禁"检测（它保护的是比赛平台的幂等台账）
- `ANSWER_FILES`（FLAG.txt 语义）改为 `DELIVERABLE_FILES`（FINDING.md / REPORT.md / EVIDENCE.md）
- `--challenge` 保留为兼容名，语义等同 `--target`

`_ctf-archive/` 里留着比赛期间的工具与数据，只作历史参考，主流程不再引用。

## 保留下来的是方法论，不是赛道知识

比赛期间真正沉淀下来的、对真实作业同样成立的东西：

**编排层**（`orchestrator.py`）
- 时钟注入：模型没有时间感，必须每轮把"现在几点、还剩多久"写进上下文
- 跨轮记忆：`MEMORY.md` 只放三类内容（已确认 / 已排除 / 悬而未决），不放原始日志
- 停滞检测：连续无进展、高比例轮次靠日志回捞、切过阶段却零裁决、悬空假设堆积
- 产出即收束：写完交付物就停，不要为"更保险"再跑一轮

**数据契约**（`models.py`）
所有跨层数据用 Pydantic 模型，不用裸 dict。教训具体：曾有一条裁决因为写成
`refuted（…）`（中文括号）而被整串比对漏掉，且不报错，闭环静默停摆好几轮。

**策略层**（`policy/scope.rego`）
范围闸从 Python 的 `if` 里挪出来，默认拒绝、可单测、可审计。
客户问"你怎么保证没打到范围外"，答案是一份策略加它的测试。

**数据层**（`store.py` / `graph.py`）
扫描产物统一成 Asset / Finding / Evidence / Edge 四模型，三层标识
（host → port → url）。查询用 DuckDB，攻击路径推理用 Kùzu 图。

**执行层**（`runner/`）
cgroup v2 硬限额 + 遍历 `cgroup.procs` 清理进程树。
解决的三个真实问题：`pkill -f` 自匹配、setsid 逃逸的孤儿进程、OOM 无法归因。

## 一句话

这套东西的价值不在"知道怎么打某类系统"，而在**强制每一条结论都可被证伪、
每一份证据都可被重放**。真实渗透里，能交付这个比能打进去更稀缺。
